## P0 尽快修：安全与丢信

### 1. 首次认领可以被抢（已核实）
- **位置**：`src/auth.ts:169`（/setup）、`:207`（/reset）、`:267`（checkApiToken）、`:513`（workerAccountId），以及 OAuth 回调。
- **问题**：只校验「令牌所在账户里有一个同名 Worker」。所有部署默认都叫 `cf-mailbox`，所以攻击者在自己的账户里建一个同名 Worker，就能认领任何还没完成首次设置的实例。`/api/me` 对未登录请求也返回 `unclaimed:true`，正好用来探测。
- **另外两条路径**：
  - 配置了 OAuth 时，第一个完成授权的任意 Cloudflare 用户直接成为管理员。
  - OAuth 认领后、account_id 还为空时，`/auth/reset` 会跳过账户比对。
- **修法**：把认领绑定到「这一次部署」。
  - workers.dev 访问：令牌所属账户的 `/workers/subdomain` 必须等于当前主机名里的子域。
  - 自定义域名访问：`/workers/domains` 里必须有当前主机名，并且指向本 Worker。
  - /reset 和 OAuth 首次认领走同一个校验。README「别人无法抢先认领」的说法要等修完才成立。

### 2. 收信的兜底不完整：会丢信，或出现「看不见的邮件」
- **位置**：`src/mail.ts:118-266`
- **INSERT 之前失败**：原文已经存好，但附件写入、KV 额度用完、查询次数超限或 CPU 超时导致失败 → 原文成为孤儿文件，messages 表里没有记录。
  - 原文 key 每次随机，重投一次就多一份孤儿。
  - 实测免费版上，附件大于约 300 KB 的邮件解析大概率超过 10 ms CPU（推断）。
- **INSERT 之后失败**：refreshThreads 或 indexMessage 出错 → 记录在，但 threads 表没有这一行。列表和搜索都查不到这封邮件；重投又被去重拦下，永远修不好。
- **修法**：
  - 存好原文后先写一条最小记录（只有信头），解析完再 UPDATE。
  - 每个附件单独 try/catch，失败就降级为「附件只在原文里」。
  - 去重命中时顺便 refreshThreads 一次，让它能自愈。
  - 原文 key 改为 hash(mailbox + Message-ID)，重投时幂等。
  - 每天对账一次孤立的记录和文件。

### 3. 免费版每次调用 50 次 D1 查询的上限
- **收信**：基础约 17–22 次，每个附件再加 1 次。约 30 个附件或内嵌图时必然失败，然后掉进第 2 条。
- **会话详情**：每封邮件读一次正文（`src/routes/messages.ts:168`），超过约 45 封的会话直接 500。
- **其他超限点**：
  - 定时发送一次领 20 封、每封约 14 次（`src/routes/compose.ts:388`）
  - 数据回填每封单独一次 FTS 插入（`src/cron.ts:48`、`messages.ts:503`），失败后游标不前进，每分钟重试一遍
  - 每天的清理、mbox 导出（每页 300 封，`src/routes/org.ts:276`）
- **修法**：合并成 `DB.batch`；详情页只加载最新几封和未读的正文；cron、导出、清理都按约 40 次的预算分批。

### 4. 定时发送可能永远卡在「发送中」
- **位置**：`compose.ts:379-403`
- **场景**：同一时刻排了多封定时邮件，一次全部被标成 sending。之后查询次数超限，catch 里那句 `UPDATE … 'failed'` 自己也超限 → 剩下的一直停在 sending。不重试、不报错，用户也取消不了（DELETE 只允许删 pending/failed）。Worker 超时也是同样结果。临时错误（429）直接标 failed，不重试。
- **修法**：领取时记录 claimed_at，并且只领预算内处理得完的数量；cron 把超时的 sending 改成 failed（不自动重发，避免重复）；允许用户取消或重试。

### 5. 垃圾邮件视图里的「永久删除」会删掉整个会话
- **位置**：`public/js/list.js:606` → `messages.ts:257`、`:291`
- **场景**：会话里只要有一封被判为垃圾邮件，整个会话就会出现在垃圾邮件视图。在这里永久删除，会先把会话里所有邮件（包括正常往来和已发送）移进废纸篓，再全部彻底删除。
- **修法**：只作用于 `spam = 1` 的邮件。

### 6. 投递状态从来没有更新过（已核实）
- **位置**：`src/routes/org.ts:364`
- **问题**：`created_at` 在 messages 和 domains 两张表里都有，SQL 报「列名有歧义」，每次都执行失败。
- **修法**：改成 `m.created_at`。

### 7. D1 每日读取额度：邮件量上来后会超额，导致收信失败
- **测算**：5 万封邮件、每天来信 100 封、开着一个标签页 8 小时，每天约读 900–1000 万行，约为免费额度的 2 倍（估算）。超额后所有查询报错，收信在第一条查询就失败。
- **主要来源**（改动都很小）：

| 来源 | 位置 | 现状（行/次） | 修法 |
|---|---|---|---|
| 侧栏统计 | `messages.ts:492` | 约 3.2 万（threads 全表扫描） | 垃圾邮件数用 mailbox_stats 汇总；稍后提醒数走已有索引；标签数改为计数表 |
| 地址计数 | `src/threads.ts:115` | 每封来信、每次打开未读都全量重算，大地址约 2 万 | 用触发器增量维护 |
| 收信时判断陌生人 | `mail.ts:207` | 约 1.7 万（主键是 (domain, address)，`WHERE address=?` 用不上） | 带上 domain，或加索引 → 1 行 |
| 轮询 | `public/js/main.js:464` | 每次读「地址数 + 3」行；catch-all 积累到 2000 个地址后，一个标签页每天约 580 万行 | 维护一个 mail_version，轮询只读一行；多个标签页只让一个轮询；出错退避 |
| 联系人补全 | `compose.ts:97` | 约 4.2 万/次，输入一个名字共 10–17 万 | 去掉 GROUP BY，沿索引 LIMIT；或在前端一次取 1–2 千个再过滤 |
| 星标、单地址、深翻页、常见词搜索 | `messages.ts:38/54/97/76` | 1.5–27 万 | 部分索引、thread_mailboxes 表、键集分页、FTS 子查询加 LIMIT |

## P1 安全（中低风险）

1. **成员越权**
   - **位置**：`compose.ts:191-268`、`threads.ts:59`、`mail.ts:46`
   - **问题**：会话会按 Message-ID 跨地址合并，只被授权 b@ 的成员能在列表里看到范围外邮件的主题和摘要，拿到它的 id 后还能把范围外的附件发到外部（performSend 没有校验附件的 messageId 和 replyToId）。
   - **修法**：这两处都调用 messageInScope；对受限成员，会话摘要只用范围内的邮件计算。
2. **全局登录限流可以被利用来锁死管理员**
   - **位置**：`src/local-auth.ts:40`
   - **问题**：用 10 个 IP 各输错 10 次，所有人的密码、通行密钥、重设入口都返回 429。`/auth/passkey/begin` 没有限流，每次都写 D1，可以被用来刷写入额度。
   - **修法**：通行密钥不计入全局阈值；IPv6 按 /64 计数；全局阈值改为加延迟；begin 改用无状态 challenge。
3. **登录 CSRF**
   - **位置**：`src/auth.ts:318`
   - **问题**：邮件里的 `<img src="/auth/magic/<token>">` 会在同源 iframe 里被请求，管理员的会话被替换成成员的。
   - **修法**：GET 只显示确认页，POST 才消费令牌；邮件正文里去掉非 cid 的相对地址。
4. **一键退订的 mailto 完全由发件人控制**
   - **位置**：`messages.ts:459`
   - **问题**：服务器会以用户自己的地址，按攻击者指定的收件人、主题和正文发信，确认框还显示的是发件人名字。
   - **修法**：校验地址；确认框显示实际收件地址；主题和正文固定。
5. **成员能改全局数据**：模板、标签名、可信发件人、全局屏蔽名单都没有管理员校验（`compose.ts:144`、`org.ts:103`、`api.ts:206`、`messages.ts:263`）。
6. **其他加固**：
   - 仍接受没有前缀的 `sid` Cookie（`auth.ts:53`）。
   - 图片代理链接的签名永不过期，而且跟随重定向（`privacy.ts:63`）。
   - 默认不设 APP_SECRET，加密密钥和带 DNS 写权限的 CF 令牌密文同在一个库（`util.ts:55`）。建议部署脚本自动生成这个 secret。
   - 通行密钥没有要求用户验证（UV）（`local-auth.ts:100`）。
7. **冒充邮件也显示品牌头像**（`public/js/util.js:127`）：DMARC 失败的 paypal.com 邮件显示了 PayPal 的 logo。应该只在验证通过时显示，失败时加警示。

## P1 可靠性（中）

- **会话归类**：
  - 不优先匹配同一个收件地址（`mail.ts:46`），同一封信发到自有的两个地址时，回复会串到别的会话。
  - 外部发件人可以伪造 References，把邮件塞进任意会话。
  - 会话跨地址后，受限成员的未读数永远清不掉。
- **删除和清理**：
  - 删除时先删记录，文件删除失败被吞掉，留下孤儿文件或幽灵会话（`mail.ts:381`）。
  - 每天只清理 300 封（`cron.ts:82`），catch-all 每天垃圾邮件超过 300 封时，积压会无限增长。
  - 修法：每分钟小批量持续清理，待删的 key 记进表里由 cron 重试。
- **存储方式可能被意外切换**（`util.ts:414`、`scripts/deploy.mjs:25`）：用 `STORAGE=r2` 切换后，下一次普通部署又会回到 lite；查询记录失败会被当成「没有记录」。两种情况旧邮件正文都会悄悄变空。应该在不一致时拒绝部署。
- **稍后提醒的会话收到新回复后不会出现**：收信时没有清除 `snooze_until`。
- **Resend 发出的邮件不保存 Message-ID**（`mail.ts:323`）：对方回复只能靠主题猜测归类，退信也关联不上原邮件。修法：自己生成并保存。
- **Cloudflare 返回不确定错误时也会切到备用服务**，可能重复发送（`src/providers.ts:44`，未确认）。
- **移除域名时不恢复原来的 MX**（`src/provision.ts:425`）：原来的 Google、M365 邮箱仍然收不到信。
- **LIKE 50 字节上限**：退信地址或成员地址很长时，查询会直接报错（`mail.ts:186`、`src/scope.ts:41`，未确认）。
- **mbox 导出按 UTF-8 解码原文**：GBK 或二进制内容会变乱码，备份是有损的（`org.ts:316`）。
- **转发会丢掉内嵌图片**（`compose.js:941`）；关页面时补发，请求体超过 64 KB 会失败，而且没有提示（`compose.js:884`）。

## P1 前端体验（均已在浏览器里复现）

1. **Enter 键被全局快捷键吞掉**（`main.js:533`，已核实）：焦点在链接、按钮、toast「撤销」上时按 Enter 没反应；没打开邮件时按 Enter，会打开收件箱第一封。
2. **双击「发送」会发出两封**（`compose.js:774`）：send() 没有防重入。
3. **列表任何刷新都跳回顶部**（`list.js:222`），包括打开邮件、归档和 30 秒轮询。
4. **在阅读区点星标、加标签会整页重渲染**：iframe 重新加载，滚动位置、手动展开的邮件、「显示图片」的选择都会丢。
5. **Esc 关菜单时会连带关掉会话或清空多选。**
6. **焦点管理**：模态框没有焦点陷阱；菜单不能用方向键操作；关闭后焦点丢失；收件人输入框没有可访问名称。
7. **回复对象可能是退信地址**：最后一封是退信时，「回复」会发给 mailer-daemon。
8. **请求失败了仍然提示「已保存」**：`settings.js:91`、`:151`、`:536`，以及 `list.js:318`。
9. **默认发件地址很随意**：代码写入了 lastFrom 但从来不读；在 sales@ 的视图里写信，也不会默认用 sales@。
10. **运行时翻译会翻译用户内容**：主题「状态：已发货」变成 "Status: 已发货"；备注「备用」变成 "Backup"；头像「我」变成 "Me"。
11. **其他小问题**：
    - 标签菜单里的颜色点被拉成长条。
    - 没有扩展名的附件，图标文字会溢出。
    - 编辑器的 selectionchange 监听从不移除，造成内存泄漏。
    - 列表没有虚拟滚动。

## P2 工程与运维

- **仓库里没有任何测试，也没有 CI。** 端到端测试只放在临时目录，这次沙箱重启就全丢了。
  - 建议把测试放进仓库 `tests/`。
  - GitHub Actions 跑三类检查：类型检查；单元测试（local-auth、storage、search 分词，以及用样例 .eml 测试收信解析，可以用 vitest + workers pool）；在 wrangler dev 上跑 Playwright 冒烟测试。
- **`lite-branch.yml` 没有限定仓库**：一键部署会把它复制到用户自己的仓库，用户每次推送都会在那边生成 lite 分支，可能触发预览构建（未确认）。加上 `if: github.repository == 'cleantempmail/cleantempmail-workspace'`。
- **一键部署的用户很难更新**：现在要靠 git 命令行。建议提供「同步上游」的 GitHub Action（手动点一下，或每周自动运行），再在应用内提示「有新版本」（对比 GitHub Release）。
- **没有版本号、发布说明和 tag。** package.json 一直是 1.0.0。
- **没有导入功能**：只能导出 mbox，从 Gmail 等迁移进来很难。
- **故障是静默的**：收信失败、额度用完时用户毫无感知。建议在设置里加「系统状态」：今日收信成功/失败数、D1 用量、最近错误。
- **前端缓存**：资源都是 `max-age=0`，而且有 3 层 import 瀑布。建议加 modulepreload，或部署时给文件名加内容哈希并配 immutable 缓存。英文界面要先等 98 KB 的词典加载完才开始请求 API，可以改成并行。
- **翻译机制**：建议从「DOM 文本替换」逐步迁移到渲染时调用 `t(key)`，用户数据一律不经过翻译。过渡期先让 Observer 只处理标了 data-i18n 的容器。
- **存储容量**：FTS 表保存了一整份正文副本，改成 contentless 可以省约 67%。主库大约在 5–7 万封时触到 500 MB（估算）。

## P3 产品功能（按价值排序）

1. **新建别名 / 随机地址**：生成地址、加备注、一键复制。这是 catch-all 产品的核心动作，现在地址页只列出用过的地址。
2. **在邮件上一键建规则**（按发件人或收件地址预填条件），并可选「应用到已有邮件」。
3. **发件地址记住上次的选择**，并跟随当前所在的地址视图。
4. **自动回复（休假回复）。**
5. **mbox 导入。**
6. **键盘与批量操作**：Shift 连选；列表里有不打开邮件的键盘光标；z 撤销。
7. **多个写信窗口或草稿切换器**；搜索结果作为独立视图并高亮关键词。

## 已确认良好

- **XSS 防护**：主站没有 XSS 漏洞；邮件正文放在沙箱 iframe 里并有独立的严格 CSP；编辑器用白名单过滤；附件只有图片和 PDF 内联打开，其余一律下载。
- **认证**：密码用 PBKDF2 哈希，并用常量时间比较；WebAuthn 的 challenge 单次使用，并校验 origin、rpIdHash 和签名计数。
- **会话与 CSRF**：会话 Cookie 带 `__Host-` 前缀，库里只存会话 id 的哈希；写请求校验 Origin 并强制 JSON。
- **收发信**：去重用部分唯一索引加 `INSERT OR IGNORE`，并发重投处理正确；定时发送用原子领取，不会重复发；Resend 请求带幂等键；一键配置先开路由再删 MX，并备份原 catch-all 规则。
- **查询**：IN 列表都做了分块，不超过 100 个参数；常规列表只读 48–188 行；cron 空闲时很轻。
- **前端完成度**：深色模式、手机端、reduced-motion、skip link 都做到位了，axe 扫描基本无问题。
